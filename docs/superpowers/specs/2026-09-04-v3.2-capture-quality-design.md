# V3.2 Capture & Quality Design

## Status

Approved implementation direction for issue #11. V3.2 starts from deployed `main` SHA `d911f7b79c2c0b5044a678d0c5f647ba988f3dbe`, which contains V3.1 plus the post-merge Pages core-gate hotfix.

V3.2 is a **test/CI visual-evidence system**. It does not add runtime capture UI, video recording, export controls, a second renderer, a second timeline, or a new application state store.

## Goal

Turn the repository's existing ad-hoc screenshot evidence into a deterministic, persistent, machine-verifiable capture contract that reviewers can inspect on every PR.

V3.2 should answer four questions reliably:

1. Did CI capture every visual checkpoint we intended to review?
2. Are those capture files valid, nontrivial PNGs with stable identities and trustworthy metadata?
3. Can a reviewer download one clearly named artifact containing the complete visual evidence matrix and summary?
4. Can the exact same PR gate detect capture-plan/wiring regressions before merge rather than leaving them for a post-merge deployment workflow?

## Existing architecture to preserve

The implementation extends existing QA rather than changing the experience:

- `src/content/chapters.ts` remains authoritative for the ten authored chapter IDs/order/copy.
- V3.0 remains authoritative for continuity, camera spline, scenes, rendering quality, and bounded black-hole behavior.
- V3.1 remains authoritative for autoplay, guided navigation, deep-links, and reduced-motion chapter-step behavior.
- V2.1 remains authoritative for WebGL recovery, privacy-first observability, diagnostics, and audio lifecycle.
- `playwright.config.ts` keeps the existing `chromium-desktop` and `chromium-mobile` projects.
- `tests/e2e/v3-boundaries.spec.ts` keeps its existing continuity assertions and attachments; V3.2 does not silently repurpose or weaken that suite.
- `.github/workflows/v2-ci.yml` remains the PR workflow and receives bounded capture-summary/upload steps.
- canonical `npm run check` already includes Node-core tests after #10 and must continue doing so.

## Why artifact contract first, not checked-in pixel baselines

V3.2 deliberately does **not** make raw pixel equality a hard merge gate.

The repository currently has no binary baseline storage/update/review policy. Chromium screenshots can also vary across runner image, font rasterization, GPU/WebGL implementation, device scale factor, and browser upgrades. Committing PNG baselines now and failing on raw diffs would introduce a noisy gate before the project has a controlled baseline lifecycle.

Instead, V3.2 establishes the prerequisites for future perceptual/pixel comparison:

- stable capture IDs;
- deterministic navigation positions;
- stabilized CSS/runtime noise;
- persistent PNG evidence;
- exact expected coverage;
- SHA-256 and image metadata;
- machine-readable manifests and summary;
- one explicit CI artifact contract.

A later version can layer reviewed baselines or perceptual metrics onto this stable evidence surface without redesigning navigation or rendering.

## Capture plan

Create `tests/e2e/support/v3.2-capture-plan.ts` as a pure, dependency-light source of truth.

### Profiles

```ts
export type CaptureProfileId = 'desktop' | 'mobile' | 'reduced-motion';
```

Each profile maps to exactly one Playwright execution path and its own output directory/manifest. Profiles never delete or rewrite another profile's files, preventing parallel Playwright project races.

### Capture case model

```ts
export type CaptureKind = 'chapter' | 'boundary';

export interface CaptureCase {
  id: string;
  profile: CaptureProfileId;
  kind: CaptureKind;
  chapterId: string;
  nextChapterId?: string;
  fraction: number;
  reducedMotion: boolean;
}
```

`chapterId` is the active/outgoing chapter. For boundary cases, `nextChapterId` is required.

All fractions are finite and bounded `0..1`. IDs and filenames are deterministic lowercase kebab-case strings derived from explicit plan values, not timestamps.

### Required matrix

#### Desktop — 19 captures

Ten chapter midpoint/hero captures, one for every authored chapter:

- `overture`
- `cold-cloud`
- `collapse`
- `ignition`
- `main-sequence`
- `red-giant`
- `shedding`
- `white-dwarf`
- `elsewhere`
- `epilogue`

Use a midpoint-like fraction (`0.50`) unless a chapter later receives an explicitly authored capture fraction.

Nine adjacent continuity boundaries at the same representative boundary fraction currently used by V3 (`0.92`):

- overture -> cold-cloud
- cold-cloud -> collapse
- collapse -> ignition
- ignition -> main-sequence
- main-sequence -> red-giant
- red-giant -> shedding
- shedding -> white-dwarf
- white-dwarf -> elsewhere
- elsewhere -> epilogue

#### Mobile — 3 captures

Representative cross-section rather than duplicating all 19 desktop captures:

- cold-cloud chapter midpoint (early volumetric material)
- red-giant -> shedding boundary (envelope/ejecta transfer)
- white-dwarf -> elsewhere boundary (alternate-branch handoff)

#### Reduced motion — 1 capture

Desktop reduced-motion representative:

- red-giant -> shedding boundary

Total required captures: **23**.

## Capture filenames and directories

Root:

```text
v3.2-captures/
```

Per profile:

```text
v3.2-captures/desktop/
v3.2-captures/mobile/
v3.2-captures/reduced-motion/
```

Each profile owns:

```text
manifest.json
<stable-capture-id>.png
```

A pure helper returns the expected relative file path for every case. The summary validator requires the manifest path to match that helper exactly; manifests cannot point to arbitrary filesystem locations.

## Browser stabilization

Create `tests/e2e/support/v3.2-capture.ts` for browser-only orchestration.

Before capture, inject **test-only** CSS:

- `html { scroll-behavior: auto !important; }`
- disable CSS animations and transitions;
- hide caret noise;
- do not hide narrative copy, journey controls, fallback UI, or visual content.

Wait for:

1. document readiness from normal `page.goto`;
2. `document.fonts.ready` when available;
3. deterministic navigation to the requested chapter fraction;
4. active chapter assertion;
5. two `requestAnimationFrame` turns after the final scroll;
6. a short bounded settle only if needed for existing R3F interpolation.

The helper must not mutate production source or expose test hooks in the runtime bundle.

### Deterministic navigation

Reuse the existing proven DOM geometry approach from `v3-boundaries.spec.ts`:

- locate `[data-chapter-id="..."]`;
- compute the element's document top and target fraction;
- scroll with browser smooth behavior disabled for the test;
- center the target fraction approximately in the viewport;
- assert `.experience-shell[data-active-chapter="..."]` before screenshot.

No autoplay timing is used to place capture checkpoints.

## PNG capture metadata

Every `page.screenshot()` returns a Buffer and writes the same bytes to the planned path.

Parse the PNG header directly without a dependency:

- require standard eight-byte PNG signature;
- read width from bytes 16..19 (big-endian UInt32);
- read height from bytes 20..23;
- reject obviously truncated buffers.

Record:

```ts
export interface CaptureManifestEntry {
  id: string;
  kind: CaptureKind;
  chapterId: string;
  nextChapterId?: string;
  file: string;
  sha256: string;
  bytes: number;
  width: number;
  height: number;
  reducedMotion: boolean;
}
```

Manifest envelope:

```ts
export interface CaptureManifest {
  schemaVersion: 1;
  profile: CaptureProfileId;
  viewport: { width: number; height: number };
  entries: CaptureManifestEntry[];
}
```

Do not put wall-clock timestamps, random run IDs, absolute runner paths, URLs, query/hash data, or environment secrets in the manifest. The manifest should be structurally deterministic for equivalent screenshot bytes.

## Integrity thresholds

V3.2 is an integrity and coverage gate, not an image-aesthetics metric.

Every PNG must:

- have the correct PNG signature;
- be at least 4 KiB;
- report positive width/height from the IHDR bytes;
- have dimensions at least as large as the CSS viewport dimensions (allowing device scale factor > 1);
- match the manifest's `bytes`, `width`, `height`, and SHA-256.

These guards catch empty/truncated/corrupt/wrong-file artifacts without pretending file size is a visual-fidelity score.

## Browser test suite

Create `tests/e2e/v3.2-capture-quality.spec.ts`.

Use one serial capture loop per profile:

- desktop test runs only in `chromium-desktop` and writes `desktop/manifest.json`;
- mobile test runs only in `chromium-mobile` and writes `mobile/manifest.json`;
- reduced-motion test runs only in `chromium-desktop`, enables `prefers-reduced-motion: reduce`, and writes `reduced-motion/manifest.json`.

For each profile:

- clear only that profile directory before writing;
- collect page/console breaking errors using the existing V3 pattern;
- run all planned cases in deterministic order;
- write each PNG and manifest entry;
- assert no breaking runtime errors;
- write the manifest only after all cases complete.

Do not delete the root `v3.2-captures` directory from a profile test because another Playwright project may be writing concurrently.

## Capture summary validator

Create `scripts/write-capture-summary.ts` and run it through Node's existing type-stripping support:

```text
node --experimental-strip-types scripts/write-capture-summary.ts v3.2-captures
```

Add npm script:

```text
capture:summary
```

### Responsibilities

The validator loads the three expected profile manifests and compares each against the pure capture plan.

Hard failures:

- missing profile manifest;
- invalid JSON/schema/profile;
- duplicate capture IDs;
- missing planned capture;
- unexpected capture;
- wrong relative filename;
- path traversal / file outside capture root;
- missing PNG;
- invalid PNG signature/truncated header;
- file < 4 KiB;
- invalid dimensions;
- dimensions smaller than CSS viewport;
- manifest byte/dimension mismatch;
- SHA-256 mismatch.

Outputs:

```text
v3.2-captures/capture-summary.json
v3.2-captures/capture-summary.md
```

Summary JSON includes:

- schema version;
- pass/fail;
- total expected/observed;
- counts by profile and kind;
- bounded error strings;
- stable ordered capture metadata.

Summary Markdown includes a compact reviewer table with profile, capture count, viewport, total bytes, and status, followed by failures if any.

The script exits nonzero on hard failures.

## Core tests

### Capture-plan contract

Create `tests/core/v3.2-capture-plan.test.ts`.

Assert:

- exactly 23 planned captures;
- desktop = 19, mobile = 3, reduced-motion = 1;
- desktop chapter captures contain exactly the ten authored public IDs (copied as an explicit test expectation, not imported through application registry resolution);
- desktop boundary captures contain all nine adjacent pairs;
- IDs and planned filenames are globally unique;
- fractions are finite and `0..1`;
- boundary cases always include `nextChapterId`;
- only reduced-motion profile sets `reducedMotion=true`.

### Summary validator contract

Create `tests/core/v3.2-capture-summary.test.ts`.

Use a temporary directory and dependency-free synthetic PNG-like buffers with valid signature/IHDR width/height plus filler bytes. Build manifests from the real plan.

Cover:

- complete valid evidence => PASS;
- missing capture => FAIL;
- duplicate/unexpected ID => FAIL;
- wrong filename/path traversal => FAIL;
- corrupt/truncated PNG => FAIL;
- byte/dimension/SHA mismatch => FAIL.

Prefer exported pure validation helpers from the summary script so tests do not rely only on subprocess output.

### CI wiring guard

Create `tests/core/v3.2-ci-wiring.test.ts`.

Assert `.github/workflows/v2-ci.yml` contains:

- browser QA;
- `npm run capture:summary` after browser QA;
- a dedicated artifact upload named `v3.2-capture-quality`;
- `v3.2-captures` in the upload path;
- `if: always()` so failed evidence remains inspectable.

Also assert `package.json` defines `capture:summary`.

## CI workflow

Extend only the existing e2e job after `Browser and visual QA`:

```text
Summarize V3.2 captures
  npm run capture:summary
```

Keep existing V2.1 diagnostics summary.

Add a separate always-upload step:

```text
Upload V3.2 capture evidence
  name: v3.2-capture-quality
  path: v3.2-captures
  if-no-files-found: warn
```

A dedicated artifact name keeps V3.2 evidence easy to find without renaming the established `v2-playwright-results` artifact.

## Failure behavior

If browser capture fails partway through a profile, the test should fail and existing Playwright artifacts remain available. Because the profile manifest is written only after successful completion, the summary will also fail closed on the missing/incomplete profile.

The V3.2 upload step runs with `if: always()` so partial PNG evidence can still be inspected.

The validator never silently invents missing entries or lowers expected capture count.

## Out of scope

V3.2 does not include:

- in-app screenshot button;
- browser MediaRecorder/video export;
- GIF/video generation;
- user download flows;
- checked-in PNG baselines;
- perceptual-diff dependency;
- automated visual approval/rebaseline mutation;
- renderer/shader redesign;
- chapter science/copy changes;
- new analytics/telemetry provider;
- deployment architecture changes.

## Merge gate

Do not merge V3.2 until the exact PR head has:

1. canonical `npm run check` SUCCESS, including Node-core V3.2 guards;
2. full Playwright `e2e` SUCCESS;
3. `npm run capture:summary` SUCCESS on the generated 23-capture matrix;
4. capture artifact upload step completed;
5. all existing V3.1 autoplay/deep-link acceptance GREEN;
6. all V3.0 continuity boundary suites GREEN;
7. all V2.1 recovery/privacy/diagnostics suites GREEN;
8. no authored chapter ID/order/copy changes;
9. review of changed files confirms no runtime feature/scope drift.

After merge, verify the merge SHA on `main` and require GitHub Pages build + artifact + deploy SUCCESS again.
